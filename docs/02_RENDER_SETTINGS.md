# Настройки рендера — справочник и пресеты
## Скорость без потери качества. Под Legion 5 / RTX 5070 Laptop / 32 GB

Это содержимое `brm/resources/presets/*.json` в человекочитаемом виде.

**Важная оговорка про имена свойств.** Точные идентификаторы RNA различаются между
Blender 4.5 / 5.0 / 5.1 / 5.2 — часть свойств переименована, часть добавлена.
Имена ниже верны для линейки 4.5–5.x, но приложение **обязано** применять их через
`safe_set()` (см. спеку, раздел 3.1) и строить UI из реального дампа capabilities.
Не хардкодить.

## 1. Cycles — сэмплирование

Главный рычаг скорости. Адаптивное сэмплирование останавливает пиксель, когда шум
упал ниже порога, поэтому «Max Samples» — это потолок, а не план работы.
**Порог шума решает всё, а не число сэмплов.**

| Свойство | Draft | Balanced | Final |
|---|---|---|---|
| `cycles.use_adaptive_sampling` | True | True | True |
| `cycles.adaptive_threshold` | 0.05 | 0.01 | 0.005 |
| `cycles.samples` (Max) | 128 | 1024 | 4096 |
| `cycles.adaptive_min_samples` | 0 (авто) | 32 | 64 |
| `cycles.time_limit` (сек/кадр) | 20 | 0 или 120 | 0 |
| `cycles.use_denoising` | False | True | True |

**`time_limit` — недооценённая функция.** Ставишь 90 секунд на кадр, и 250-кадровая
анимация гарантированно уложится в 6 часов ночью, а не в непредсказуемые 14.
Кадры добираются денойзером. Для дедлайна это лучше, чем угадывать сэмплы.
Минус — сложные кадры получатся шумнее простых, качество «плавает». Для финала — 0.

`adaptive_min_samples` = 0 означает автоподбор. Ставить 32–64 стоит для анимации:
слишком ранний выход на некоторых пикселях даёт разное поведение от кадра к кадру,
и это читается как мерцание.

**Sampling pattern.** В новых версиях появился Blue-Noise паттерн
(`cycles.sampling_pattern`), заметно лучше распределяющий шум на низких сэмплах.
Список доступных значений берём из capabilities и подставляем лучший из доступных.

**Seed.** `cycles.seed` + `cycles.use_animated_seed`:
- Анимированный сид — шум разный каждый кадр, после денойза это «кипящая» плёнка.
- Фиксированный сид — шум одинаковый, при статичной камере выглядит как прилипшая
  грязь, но после денойза стабильнее.
Для анимации по умолчанию **фиксированный**. Дать переключатель, это вкусовое.

**Scrambling Distance** (`cycles.auto_scrambling_distance = True`,
`cycles.scrambling_distance = 1.0`) — на GPU даёт 10–30% ускорения на простых сценах
за счёт лучшей когерентности лучей. На сценах с сильным DOF/motion blur может дать
корреляционные артефакты. Включать в Draft/Balanced, проверять глазами.

## 2. Cycles — Light Paths

| Свойство | Draft | Balanced | Final | Комментарий |
|---|---|---|---|---|
| `cycles.max_bounces` | 4 | 8 | 12 | общий потолок |
| `cycles.diffuse_bounces` | 1 | 3 | 4 | |
| `cycles.glossy_bounces` | 2 | 4 | 4 | |
| `cycles.transmission_bounces` | 2 | 8 | 12 | стекло, вода — не жалеть |
| `cycles.volume_bounces` | 0 | 1 | 2 | дым/туман очень дорогой |
| `cycles.transparent_max_bounces` | 4 | 8 | 8 | листва, alpha-карты |
| `cycles.sample_clamp_direct` | 0 | 0 | 0 | |
| `cycles.sample_clamp_indirect` | 5 | 10 | 10 | против firefly |
| `cycles.blur_glossy` (Filter Glossy) | 2.0 | 1.0 | 0.5 | |
| `cycles.caustics_reflective` | False | False | False | |
| `cycles.caustics_refractive` | False | False | False | |

Каустики выключены везде не случайно: они дают основную массу белых точек-светлячков
и требуют огромного числа сэмплов. Если каустика нужна художественно — включай
адресно на конкретном объекте (Shadow Caustics), а не глобально.

`sample_clamp_indirect` — компромисс. 10 убирает светлячки почти без потери энергии.
Ниже 5 начинает съедать блики и делает картинку плоской.

**Light Tree** (`cycles.use_light_tree`): включён — правильный выбор для сцен с
десятками источников (твоя пещера с эмиссивными кристаллами). Для сцены с 1–3
источниками его отключение даёт небольшой прирост.

**Fast GI Approximation** — сильно недооценённый ускоритель для интерьеров, пещер и
объёмов:
```
cycles.use_fast_gi = True
cycles.fast_gi_method = 'ADD'   # 'REPLACE' — быстрее, грубее
cycles.ao_bounces_render = 2    # после 2-го отскока GI заменяется на AO
```
На замкнутых сценах с множественными переотражениями это может дать ускорение в разы.
На открытых сценах эффект близок к нулю. Включать осознанно, в Balanced — да, в Final — нет.

## 3. Cycles — объёмы, производительность, VRAM

### Объёмы (критично для пещеры, песка, дыма)

| Свойство | Draft | Balanced | Final |
|---|---|---|---|
| `cycles.volume_step_rate` | 4.0 | 2.0 | 1.0 |
| `cycles.volume_max_steps` | 256 | 512 | 1024 |
| `cycles.volume_preview_step_rate` | 8.0 | 4.0 | 4.0 |

`volume_step_rate` — множитель шага. 2.0 означает вдвое более грубые шаги и примерно
вдвое быстрее. Для мягкого тумана разница почти незаметна, для плотного дыма с
резкими деталями — видна сразу.

### Производительность

```
render.use_persistent_data = True     # держит BVH между кадрами
cycles.use_auto_tile       = True
cycles.tile_size           = 2048     # при нехватке VRAM → 1024 или 512
render.threads_mode        = 'AUTO'
cycles.device              = 'GPU'
preferences.addons['cycles'].preferences.compute_device_type = 'OPTIX'
```

**Persistent Data — главный ускоритель анимации.** Blender не пересобирает BVH и не
перезагружает текстуры каждый кадр. Выигрыш на статичной геометрии — десятки
процентов. Цена: постоянно занятая RAM. **На 32 GB с тяжёлой сценой (симуляция,
FLIP-кэш, 1000+ фрагментов) это прямой путь к out of memory.** Поэтому в BRM это
чекбокс с предупреждением, включённый по умолчанию только в пресетах Preview/Balanced,
и выключенный в пресетах для тяжёлых сцен.

**Tile size** влияет на пиковую VRAM. При ошибке нехватки памяти уменьшать первым делом.

### Simplify — аварийный рычаг при нехватке VRAM

```
render.use_simplify                  = True
render.simplify_subdivision_render   = 3
render.simplify_child_particles_render = 1.0
render.simplify_volumes              = 1.0
cycles.texture_limit_render          = '4096'   # 'OFF','128'...'8192'
```

`texture_limit_render` — самый эффективный способ впихнуть сцену в VRAM ноутбучной
карты. Ограничение 2048 на сцене с десятком 4K-текстур освобождает гигабайты, а на
финальном кадре при 1080p разница часто не читается. Для крупных планов — не трогать.

## 4. Cycles — денойз

```
cycles.use_denoising          = True
cycles.denoiser               = 'OPENIMAGEDENOISE'   # 'OPTIX' — быстрее, грубее
cycles.denoising_input_passes = 'RGB_ALBEDO_NORMAL'
cycles.denoising_prefilter    = 'ACCURATE'
cycles.denoising_quality      = 'HIGH'               # HIGH / BALANCED / FAST
cycles.denoising_use_gpu      = True
```

`RGB_ALBEDO_NORMAL` обязателен: без albedo и normal денойзер размазывает текстуры и
съедает мелкую геометрию. `denoising_use_gpu` ускоряет сам денойз, но занимает
дополнительную VRAM — при пограничной сцене отключить.

### Денойз анимации — отдельная тема

Кадровый денойз не знает о соседних кадрах, поэтому даёт «кипение» — самый частый
дефект в анимациях. Три стратегии:

1. **Простая.** Порог шума ≤ 0.01, `adaptive_min_samples` ≥ 32, фиксированный сид.
   Для большинства задач достаточно.
2. **Правильная.** Рендерить в **Multilayer EXR с денойз-пассами** без денойза в
   рендере (`Denoising Data` в Passes), а денойзить нодой Denoise в композиторе.
   Можно перебирать настройки денойза без перерендера — на ноутбуке это экономит часы.
3. **Комбинированная.** Рендер с денойзом + запись сырых пассов на всякий случай.
   Дороже по диску, зато есть путь отступления.

BRM должен уметь включать `view_layer.cycles.denoising_store_passes = True`
одним чекбоксом «Сохранить денойз-пассы».

## 5. EEVEE (Next, 4.2+ / 5.x)

EEVEE — не «быстрый Cycles», у него другие узкие места: тени, объёмы и трассировка
экранного пространства. Идентификатор движка получаем из capabilities, он менялся
между версиями (`BLENDER_EEVEE_NEXT` → `BLENDER_EEVEE`).

| Свойство | Draft | Balanced | Final |
|---|---|---|---|
| `eevee.taa_render_samples` | 16 | 64 | 128–256 |
| `eevee.use_shadows` | True | True | True |
| `eevee.shadow_ray_count` | 1 | 2 | 3 |
| `eevee.shadow_step_count` | 2 | 4 | 6 |
| `eevee.use_raytracing` | False | True | True |
| `eevee.use_volumetric_shadows` | False | True | True |
| `eevee.volumetric_tile_size` | '8' | '4' | '2' |
| `eevee.volumetric_samples` | 32 | 64 | 128 |
| `eevee.use_overscan` | True | True | True |
| `eevee.overscan_size` | 3.0 | 5.0 | 5.0 |

**Raytracing** (`eevee.ray_tracing_options`): `resolution_scale` = `'2'` (половинное
разрешение) в Balanced, `'1'` в Final. Это второй по значимости параметр после сэмплов.

**Clamping.** В EEVEE Next есть отдельные клампы (`clamp_surface_direct`,
`clamp_surface_indirect`, `clamp_volume_direct`, `clamp_volume_indirect`,
`clamp_world`) — их наличие проверять через capabilities. Работают как в Cycles:
режут светлячки от ярких источников и HDRI.

**Мерцание в EEVEE-анимации** — почти всегда одно из трёх:
1. Мало `taa_render_samples` при включённых мягких тенях. Лечится числом ≥ 64.
2. Jittered shadows у источников света — красиво в статике, мерцает в движении.
   Либо повышать сэмплы, либо отключать джиттер на конкретной лампе.
3. Временной денойз трассировки (`ray_tracing_options.denoise_temporal`) —
   при быстром движении даёт шлейфы. Отключить и добрать сэмплами.

**Overscan** обязателен, если в кадре есть SSR, отражения или motion blur: без него
эффекты обрываются у границ кадра. 3–5% достаточно.

**Bloom в EEVEE Next убран** — свечение теперь делается нодой Glare в композиторе.
Если старая сцена рассчитывала на bloom, картинка приедет тусклой.

## 6. Вывод, форматы и кодеки

### Железное правило

**Никогда не рендерить анимацию сразу в видеофайл.** Падение на 240-м кадре из 250
уничтожает всю работу, докрутить невозможно. Только секвенция кадров, сборка видео —
отдельным шагом. BRM должен предупреждать, если в файле выставлен FFMPEG-вывод.

### Промежуточные форматы

| Задача | Формат | Настройки |
|---|---|---|
| Простой рендер без компа | PNG | RGBA, 16 bit, compression 15% |
| Есть композитинг / грейд | OpenEXR | Half Float, кодек **DWAA** |
| Мастер-архив, макс. качество | OpenEXR | Half Float, кодек **ZIP** (без потерь) |
| Пассы, Cryptomatte | OpenEXR Multilayer | Half Float, ZIP |

PNG compression — это скорость записи, не качество. На 15% файл чуть больше, но кадр
сохраняется заметно быстрее; при коротких кадрах экономия набегает.

DWAA — сжатие с потерями, но визуально неотличимо и уменьшает файл в разы против ZIP.
Для промежуточных кадров под грейд — оптимально. Для архива — ZIP.

Half Float (16 бит) вместо Full Float (32) режет размер вдвое. Full нужен только под
экстремальный грейд с вытягиванием пересветов на много стопов.

### Color management

```
scene.view_settings.view_transform = 'AgX'      # 'Filmic', 'Standard'
scene.view_settings.look           = 'None'
scene.view_settings.exposure       = 0.0
scene.sequencer_colorspace_settings.name = 'sRGB'
```

AgX — дефолт с Blender 4.0, мягче обрабатывает пересветы, чем Filmic, но заметно
десатурирует яркие цвета. Для рекламных креативов с насыщенными цветами часто
приходится добавлять Look со средним контрастом или уходить в Standard и грейдить
снаружи.

View Transform **не влияет** на данные в EXR (там линейный свет), только на PNG,
JPEG и видео. Если пайплайн через EXR → Resolve, ставь то, что удобно для превью.

### Сборка видео внешним ffmpeg

Мастер для монтажа (ProRes 422 HQ, большой файл, быстро декодируется):
```bash
ffmpeg -framerate 25 -i "D:\out\shot\%04d.png" ^
  -c:v prores_ks -profile:v 3 -pix_fmt yuv422p10le ^
  -vendor apl0 "D:\out\shot_master.mov"
```

Финальная выдача H.264 (универсально, играется везде):
```bash
ffmpeg -framerate 25 -i "D:\out\shot\%04d.png" ^
  -c:v libx264 -crf 17 -preset slow -pix_fmt yuv420p ^
  -colorspace bt709 -color_primaries bt709 -color_trc bt709 ^
  -movflags +faststart "D:\out\shot_h264.mp4"
```

H.265 (меньше вес при том же качестве, хуже совместимость):
```bash
ffmpeg -framerate 25 -i "D:\out\shot\%04d.png" ^
  -c:v libx265 -crf 20 -preset slow -pix_fmt yuv420p ^
  -tag:v hvc1 -movflags +faststart "D:\out\shot_h265.mp4"
```

Вертикаль под соцсети и рекламные креативы (1080×1920, 30 fps):
```bash
ffmpeg -framerate 30 -i "D:\out\shot\%04d.png" ^
  -vf "scale=1080:1920:flags=lanczos" ^
  -c:v libx264 -crf 18 -preset slow -pix_fmt yuv420p ^
  -profile:v high -level 4.1 -movflags +faststart "D:\out\shot_vertical.mp4"
```

Про CRF: 17 — практически неотличимо от исходника, 20 — хорошо, 23 — дефолт ffmpeg,
уже видны артефакты на градиентах и дыме. Для тёмных сцен с дымом и объёмами бери
16–17, иначе получишь бандинг в тенях. `-preset slow` даёт лучший битрейт при том же
CRF ценой времени кодирования — на 250 кадрах это минуты, не часы.

`-pix_fmt yuv420p` обязателен, иначе Windows-плееры, соцсети и браузеры откажутся
проигрывать файл.

### Если всё же кодировать внутри Blender

```
image_settings.file_format = 'FFMPEG'
ffmpeg.format              = 'MPEG4'
ffmpeg.codec               = 'H264'
ffmpeg.constant_rate_factor = 'HIGH'      # PERC_LOSSLESS / HIGH / MEDIUM
ffmpeg.ffmpeg_preset       = 'GOOD'
ffmpeg.gopsize             = 18
ffmpeg.audio_codec         = 'NONE'
```

## 7. Композитор

Композитор считается **на каждом кадре** и может незаметно съедать больше времени,
чем сам рендер — особенно ноды Glare, Blur и Denoise на 4K.

```
render.use_compositing = True/False
render.use_sequencer   = False          # секвенсор может подменить картинку
render.compositor_device = 'GPU'        # GPU-компоузер, 4.2+
render.compositor_precision = 'AUTO'    # 'FULL' при бандинге в градиентах
```

Три вещи, которые надо помнить:

1. **`use_sequencer = False` для рендера кадров.** Если в файле остался мусор в
   Video Sequencer, Blender отрендерит его вместо 3D-сцены. Классическая потеря
   ночи. BRM должен явно выключать секвенсор, если пользователь не просил обратного.

2. **GPU-компоузер** ускоряет тяжёлые ноды в разы, но не все ноды поддержаны и он
   конкурирует за VRAM с рендером. При ошибках памяти — вернуть на CPU.

3. **Ловушка API в Blender 5.x:** доступ к дереву композитора изменился —
   `scene.node_tree` заменён на `scene.compositing_node_group`. Скрипты,
   написанные для 4.x, тихо падают. В override-скрипте BRM обращение к композитору
   должно идти через проверку обоих вариантов.

Отдельная опция в UI: **«Отключить композитор на этот рендер»**. Полезно, когда надо
получить чистые кадры быстро, не трогая файл.

## 8. Готовые пресеты

### Draft — проверка анимации, движения, таймингов
Cycles: порог 0.05, max 128, без денойза, отскоки 4, resolution 50%, time limit 20 с,
Simplify вкл (subdiv 2, texture limit 1024), Persistent Data вкл, вывод JPEG 90%.
Задача — увидеть движение за минуты, а не оценить картинку.

### Preview — показать клиенту черновик
Cycles: порог 0.02, max 512, денойз OPTIX, отскоки 6, resolution 100%,
Fast GI вкл, вывод PNG 8 bit.

### Balanced — рабочий дефолт, ночной рендер
Cycles: порог 0.01, max 1024, min samples 32, денойз OIDN + Albedo/Normal,
отскоки 8/3/4/8/1/8, clamp indirect 10, каустики выкл, Persistent Data вкл,
tile 2048, вывод PNG 16 bit или EXR Half DWAA.
Это то, что запускается на ночь.

### Final — финальная выдача
Cycles: порог 0.005, max 4096, min samples 64, денойз OIDN HIGH + ACCURATE,
отскоки 12/4/4/12/2/8, Fast GI выкл, volume step 1.0,
вывод OpenEXR Multilayer Half ZIP + денойз-пассы + Cryptomatte.

### Heavy Scene — тяжёлая симуляция, риск нехватки памяти
Balanced, но: Persistent Data **выкл**, tile 512, texture limit 2048,
chunking по 20 кадров, денойз на CPU.
Для сцен с FLIP-кэшем и тысячами фрагментов.

### Social 9:16 — рекламный креатив
1080×1920, 30 fps, Balanced-настройки, вывод PNG 16 bit,
автосборка в H.264 CRF 18 с `+faststart`.

## 9. Порядок действий при медленном рендере

Если кадр считается слишком долго — проверять именно в этом порядке, сверху даёт
максимальный выигрыш:

1. Устройство — точно OPTIX, а не CPU? (`--cycles-print-stats` покажет)
2. Порог шума — 0.01 вместо 0.001?
3. Каустики выключены?
4. Разрешение / процент разрешения — не рендерим ли 4K там, где нужен 1080p?
5. Объёмы — `volume_step_rate` поднят до 2.0?
6. Persistent Data включён (если RAM позволяет)?
7. Отскоки — не 32 ли по умолчанию из старого файла?
8. Композитор и секвенсор — не считают ли лишнее каждый кадр?
9. Simplify + texture limit — не упёрлись ли в VRAM с постоянным свопом?
10. Fast GI — если сцена замкнутая.

Если кадр падает по памяти — обратный порядок: сначала texture limit, потом tile size,
потом Persistent Data, потом денойз на CPU, потом chunking.

## 10. Мерцание в анимации — сводный чеклист

Дефекты разбросаны по разделам выше, здесь собраны в один порядок проверки.
Пресет **Anti-flicker** в приложении = пункты 1–4 разом.

**Cycles**

1. Порог шума ≤ 0.01 и `adaptive_min_samples` ≥ 32. Ранний выход адаптивного
   сэмплирования на разных пикселях от кадра к кадру читается именно как мерцание.
2. `use_animated_seed = False`. Стабильный паттерн шума денойзится стабильнее.
3. Денойз с `RGB_ALBEDO_NORMAL` и `prefilter = ACCURATE`. Без вспомогательных
   пассов денойзер каждый кадр «додумывает» текстуру заново.
4. `sample_clamp_indirect = 10`. Одиночный светлячок, появившийся на трёх кадрах
   из ста, выглядит как вспышка.
5. Если мерцание осталось — рендерить в **Multilayer EXR с денойз-пассами** без
   денойза в рендере и денойзить в композиторе. Тогда параметры денойза можно
   перебирать без перерендера. На ноутбуке это единственный вменяемый путь.
6. Scrambling Distance выключить: на сценах с DOF и motion blur он даёт
   корреляционные артефакты, которые в движении заметны сильнее, чем в статике.

**EEVEE**

7. `taa_render_samples` ≥ 64. Ниже мягкие тени не успевают сойтись.
8. Jittered shadows у источников света отключить или добрать сэмплами.
9. Временной денойз трассировки (`denoise_temporal`) — при быстром движении даёт
   шлейфы; отключить и компенсировать сэмплами.

**Не про движок**

10. Текстурные координаты у анимированной геометрии: Generated пересчитываются от
    bounding box каждый кадр, отсюда «ползущая» текстура. Object-координаты со
    статичным Empty решают.
11. Тени от систем частиц: проверить Ray Visibility → Shadow на эмиттере.
12. Симуляции, которые не досчитаны в кэш, дают разную геометрию на разных
    запусках. Перед ночным рендером — Bake, а не рассчёт на лету.
