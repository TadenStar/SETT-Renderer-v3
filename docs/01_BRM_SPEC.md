# BRM — Blender Render Manager
## Техническое задание v0.1

Рабочее имя проекта: **BRM**. Репозиторий: `blender-render-manager`.

---

## 1. Что это

Десктопное приложение под Windows, которое запускает Blender в фоновом режиме
(`blender -b`), управляет очередью рендера, показывает живой прогресс и применяет
пресеты настроек, не трогая сам `.blend` файл.

Целевое железо (учтено в дефолтах): Legion 5 OLED, i9 / 32 GB RAM / RTX 5070 Laptop.
Одна машина, фермы нет. Все дефолты рассчитаны на ночной рендер с термотроттлингом
(закладывай +20–30% ко времени).

---

## 2. Стек

**Рекомендация: Python 3.11+ и PySide6 (Qt).**

Почему именно это:
- Blender сам на Python — override-скрипты и код приложения на одном языке.
- `QProcess` даёт живое чтение stdout Blender без подвисаний UI.
- Сборка в один `.exe` через PyInstaller.
- Нет второго рантайма (Node/Chromium), приложение стартует мгновенно.

Альтернатива (Electron / Tauri + React) даст более красивый UI, но потребует два языка
и IPC-слой между фронтом и процессом Blender. Для v1 это лишняя сложность.

Зависимости: `PySide6`, `pydantic` (валидация пресетов), `psutil` (мониторинг RAM/GPU),
`ffmpeg` — внешним бинарником, не библиотекой.

---

## 3. Ключевое архитектурное решение

**У Blender мало флагов командной строки.** Через CLI можно задать только:
движок, сцену, диапазон кадров, путь вывода, формат, число потоков и устройство Cycles.
Сэмплы, отскоки, денойз, EEVEE, симплифай — через CLI **не передаются**.

Поэтому BRM работает так:

```
[UI пресета]  →  [генератор override.py]  →  временный .py в %LOCALAPPDATA%\BRM\tmp\
                                                      ↓
              blender.exe -b scene.blend --python override.py -o ... -a
```

Все настройки применяются Python-скриптом **внутри** запущенного Blender, после
загрузки файла и до старта рендера. Исходный `.blend` не изменяется — правки живут
только в памяти процесса.

### 3.1 Правило safe_set — обязательное

Имена RNA-свойств различаются между Blender 4.5 / 5.0 / 5.1 / 5.2. Жёстко зашивать
их нельзя. Каждое присваивание идёт через обёртку:

```python
def safe_set(obj, attr, value, log):
    if obj is None:
        log.append(f"SKIP {attr}: owner is None")
        return False
    if not hasattr(obj, attr):
        log.append(f"SKIP {attr}: not available in this Blender build")
        return False
    try:
        setattr(obj, attr, value)
        log.append(f"OK   {attr} = {value!r}")
        return True
    except Exception as e:
        log.append(f"FAIL {attr}: {e}")
        return False
```

Лог применения печатается в stdout с префиксом `[BRM]` и показывается в приложении
отдельной вкладкой «Applied settings». Пользователь всегда видит, что реально
применилось, а что версия не поддержала.

### 3.2 Интроспекция возможностей (capabilities probe)

Когда пользователь первый раз указывает `blender.exe`, BRM один раз запускает пробу
и кэширует результат в `capabilities_<hash>.json`:

```bash
blender.exe -b --factory-startup --python probe_caps.py
```

`probe_caps.py` выгружает в JSON:
- `bpy.app.version` и `version_string`;
- список движков: `[e.bl_idname for e in bpy.types.RenderEngine.__subclasses__()]`
  плюс встроенные (`CYCLES`, `BLENDER_EEVEE*`, `BLENDER_WORKBENCH`) — точный
  идентификатор EEVEE зависит от версии (`BLENDER_EEVEE_NEXT` в 4.2–4.5,
  переименован в 5.x), поэтому **определяем его, а не угадываем**;
- все свойства `bpy.types.CyclesRenderSettings`, `bpy.types.SceneEEVEE`,
  `bpy.types.RenderSettings`, `bpy.types.ImageFormatSettings`,
  `bpy.types.CyclesPreferences` — с типом, диапазоном (`soft_min/soft_max`),
  списком enum-значений и дефолтом;
- доступные устройства Cycles (`OPTIX`, `CUDA`, `HIP`, `ONEAPI`) и их имена.

**Из этого JSON приложение строит UI настроек динамически.** Не хардкодим форму —
рисуем виджеты по типу свойства: bool → чекбокс, enum → комбобокс, int/float →
спинбокс с реальными границами. Приложение автоматически переживает апдейт Blender.

Пункт «настройки динамические и для каждого движка свои» из твоего ТЗ решается именно так.

### 3.3 Проба проекта (project probe)

При выборе `.blend` — второй запуск, читаем без рендера:

```bash
blender.exe -b "project.blend" --python probe_scene.py
```

Возвращает: список сцен, view layers, камер, `frame_start/end/step`, fps,
разрешение и процент, текущий движок, путь вывода из файла, список маркеров,
наличие композитора и секвенсора, список включённых аддонов, которых требует файл.

Это даёт UI: выпадающий список сцен и камер, автоподстановку диапазона кадров.

## 4. Функциональные требования

### 4.1 Настройки приложения (глобальные, один раз)

| Поле | Поведение |
|---|---|
| Путь к `blender.exe` | Выбор файлом. После выбора — запуск capabilities probe. Кэш по хешу пути + mtime |
| Несколько версий Blender | Список профилей: 4.5 LTS / 5.1 / 5.2. Переключение в один клик |
| Путь к `ffmpeg.exe` | Опционально. Если пусто — сборка видео отключена |
| Папка вывода по умолчанию | |
| Автовыключение ПК после очереди | Чекбокс + задержка 60 с с отменой |
| Тема | Светлая / тёмная |

Хранение: `%APPDATA%\BRM\settings.json`.

**Требование из ТЗ — индикация незаданного Blender.** Реализуем тремя уровнями:
1. Кнопка «Рендер» неактивна (`setEnabled(False)`) с тултипом «Не выбран blender.exe».
2. Постоянная плашка-баннер вверху окна оранжевого цвета: «Blender не настроен →
   Открыть настройки». Кликабельная, ведёт прямо в нужное поле.
3. При первом запуске — модальный онбординг-диалог, который сразу просит указать путь.

Плюс валидация: файл существует, это действительно Blender (probe вернул версию),
версия не ниже 4.2. Если Blender переустановили и путь протух — баннер возвращается.

### 4.2 Окно проекта

- Поле пути к `.blend` (кнопка выбора + drag & drop файла в окно).
- Список последних 10 проектов.
- После загрузки — сводка: версия Blender, в которой сохранён файл (предупреждение,
  если она новее выбранного бинарника), сцены, камеры, диапазон кадров, разрешение.
- Выбор сцены (`-S`) и view layer.
- Диапазон кадров: «из файла» / вручную / одиночный кадр / список кадров `1,5,10..20`.
- Frame step (`-j`) — для быстрого превью каждого 4-го кадра.
- Путь и шаблон вывода: `D:\out\{project}\{scene}\{preset}\####`.
  Плейсхолдеры разворачиваются приложением, `####` уходит в Blender как есть.

### 4.3 Настройки рендера

Две панели, переключаются по выбранному движку. Наполнение — из
`02_RENDER_SETTINGS.md` и `resources/presets/*.json`.

Режимы отображения:
- **Пресет** — выпадающий список: Draft / Preview / Balanced / Final / Social 9:16.
- **Простой** — 6–8 главных ползунков (сэмплы, порог шума, отскоки, денойз,
  разрешение %, формат).
- **Экспертный** — вся сгенерированная из capabilities форма с поиском по названию
  свойства и подсветкой изменённых относительно пресета значений.

Каждый параметр может быть в состоянии **«не трогать»** (три состояния вместо двух).
Это важно: если художник настроил сцену вручную, приложение не должно перетирать
всё подряд. По умолчанию override применяется только к явно включённым полям.

### 4.4 Запуск и мониторинг

- Кнопка «Рендер» → сборка команды → `QProcess.start()`.
- Панель «Команда»: показывает итоговую строку запуска с кнопкой «Копировать».
  Обязательно — это главный инструмент отладки.
- Живой лог с фильтрами: всё / только `[BRM]` / только ошибки.
- Прогресс-бар двухуровневый: кадр X из N, и сэмплы внутри кадра.
- Строка статуса: текущий кадр, сэмплы, память, время кадра, ETA всей задачи.
- Кнопки: Пауза (после текущего кадра), Стоп (terminate → kill через 5 с).
- График времени кадров (простой sparkline) — сразу видно, где сцена тяжелеет.

### 4.5 Очередь — лёгкая версия

Модель задачи (`.blend` + сцена + диапазон + пресет + вывод) закладываем сразу,
с первого этапа: даже одиночный рендер описывается ею. Но UI в v1 минимальный —
простой список, куда можно добавить две-три задачи, и последовательный прогон.

Приоритеты, drag & drop, планировщик по времени — отложены. Состояние сохраняется
в `queue.json`, чтобы пережить перезапуск и падение.

### 4.6 Resume — докрутка недостающих кадров

Перед стартом сканируем папку вывода, вычитаем существующие кадры из диапазона,
рендерим только недостающие через `--render-frame 12,17,40..55`. Обязательная
функция для ноутбука, который может уйти в сон или упасть по VRAM.

Опция «перерендерить кадры меньше N килобайт» — ловит битые/пустые файлы.

### 4.7 Chunking

Длинную анимацию бьём на пачки по 20–50 кадров, каждая — отдельный процесс Blender.
Зачем: утечки памяти в тяжёлых сценах не накапливаются, падение убивает одну пачку,
а не весь ночной рендер. Минус — пересборка BVH на старте каждой пачки, поэтому
размер пачки настраиваемый и по умолчанию отключён для лёгких сцен.

### 4.8 Постобработка

После успешной задачи — опциональная сборка секвенции в видео внешним ffmpeg
(команды в `02_RENDER_SETTINGS.md`, раздел 6). Прогресс ffmpeg парсим по `frame=`.

### 4.9 Уведомления и история

- Системное уведомление Windows по завершении задачи и очереди.
- SQLite `history.db`: дата, проект, пресет, кадров, общее время, среднее на кадр,
  пик памяти, статус. Экран истории с сортировкой — становится личной базой
  бенчмарков: «этот шот рендерился 6 часов на Balanced».

## 5. Сборка команды запуска

Порядок аргументов **критичен**. Blender выполняет их слева направо: `-o`, указанный
после `-a`, не подействует, а загрузка `.blend` перетирает ранее заданный вывод.

Каноническая форма BRM:

```
"<blender.exe>"
  -b "<project.blend>"
  [-S "<SceneName>"]
  --python "<tmp>\_brm_override_<uuid>.py"
  -o "<output>\####"
  -F PNG
  -x 1
  [-s <start> -e <end>] [-j <step>]
  [-t 0]
  -a                       ← или --render-frame <list> вместо -s/-e/-a
  --                       ← всё после двойного тире уходит в аддон Cycles
  --cycles-device OPTIX
  --cycles-print-stats
```

Заметки, которые надо учесть в коде:

- `-b` (background) обязателен, иначе откроется окно.
- `--factory-startup` ускоряет старт и убирает влияние пользовательских настроек,
  **но отключает аддоны**. Для сцен с FLIP Fluids, CellFracture-геометрией или
  кастомными нодами это сломает рендер. Дефолт — **выключено**, чекбокс с явным
  предупреждением в тултипе.
- `--cycles-device` работает только для Cycles и только после `--`. Значения:
  `CPU CUDA OPTIX HIP ONEAPI METAL`, к GPU можно добавить `+CPU` (`OPTIX+CPU`).
  Для RTX 5070 корректный выбор — `OPTIX`.
- `-F` принимает `PNG BMP JPEG TIFF TGA IRIS HDR`, а также, если скомпилировано:
  `OPEN_EXR OPEN_EXR_MULTILAYER FFMPEG CINEON DPX JP2 WEBP`.
- Число `#` в пути = число цифр в имени кадра. `####` → `0001.png`.
- `-x 1` добавляет расширение файла.
- Одиночные кадры и списки: `--render-frame 1,5,10..20` (без пробелов).
- `-E`/`--engine` можно не передавать: движок надёжнее ставить внутри override.py,
  потому что идентификатор EEVEE меняется между версиями. `-E help` выводит список.
- Русские буквы и пробелы в путях: обязательно `subprocess`/`QProcess` со списком
  аргументов, а не одной строкой. И `encoding="utf-8", errors="replace"` при чтении
  stdout, иначе на кириллических путях приложение упадёт на декодировании.

Переменные окружения процесса: `PYTHONUNBUFFERED=1` — иначе прогресс придёт пачкой
в конце, а не построчно.

## 6. Парсинг вывода Blender

Blender печатает прогресс в stdout, перезаписывая строку через `\r`. Читать нужно
по любому из `\r` и `\n`, иначе прогресс-бар не двинется до конца кадра.

Опорные шаблоны:

```python
RE_FRAME    = re.compile(r"^Fra:(\d+)")
RE_SAMPLE   = re.compile(r"Sample (\d+)/(\d+)")
RE_MEM      = re.compile(r"Mem:([\d.]+)([MG])")
RE_PEAK     = re.compile(r"Peak(?: Mem)?[: ]+([\d.]+)([MG])")
RE_REMAIN   = re.compile(r"Remaining:([\d:.]+)")
RE_SAVED    = re.compile(r"^Saved: '(.+)'")
RE_TIME     = re.compile(r"^ Time: ([\d:.]+)")
RE_QUIT     = re.compile(r"^Blender quit")
RE_ERROR    = re.compile(r"(Error:|Traceback \(most recent call last\)|CUDA error|OptiX error|out of memory|Cannot read file)")
```

Строка Cycles выглядит примерно так:
`Fra:12 Mem:1024.55M (Peak 1200.00M) | Time:00:12.34 | Remaining:00:05.00 | Scene, ViewLayer | Sample 128/512`

EEVEE печатает `Rendered N/M samples` вместо `Sample N/M` — держи оба шаблона.
Точные формулировки лучше не угадывать: при первом запуске каждого движка сохраняй
сырой лог, парсер должен деградировать мягко (нет совпадения → показываем кадры,
без сэмплов), а не падать.

ETA считаем не по `Remaining` от Blender (он про текущий кадр), а по скользящему
среднему последних 5 кадров × число оставшихся кадров. Так честнее.

Коды выхода: 0 — успех. Ненулевой — задача помечается упавшей, лог сохраняется
рядом с выводом в `render_log_<timestamp>.txt`.

Отдельно ловим `out of memory` — это самый частый отказ на ноутбучной 5070.
При этой ошибке приложение предлагает конкретное действие: снизить Texture Limit,
уменьшить tile size, выключить Persistent Data. Не абстрактное «ошибка рендера».

## 8. Этапы разработки

Каждый этап — отдельная ветка и отдельный PR. Не начинать следующий, пока
предыдущий не запускается.

| Этап | Содержание | Критерий готовности |
|---|---|---|
| **M0** | Скелет PySide6, окно, `settings.json`, выбор `blender.exe`, баннер «не настроен» | Приложение стартует, путь сохраняется между запусками |
| **M1** | `probe_caps.py` + кэш capabilities; `probe_scene.py` + панель проекта | Выбрал `.blend` — вижу сцены, камеры, диапазон кадров |
| **M2** | `command_builder` + `override_builder`, запуск, сырой лог, кнопка «Копировать команду» | Рендерится один кадр с дефолтными настройками |
| **M3** | `log_parser`, прогресс-бары, ETA, Стоп/Пауза, обработка кодов выхода | Виден живой прогресс анимации, стоп работает |
| **M4** | **JSON-пресеты + простая форма** (6–8 главных параметров). Пресеты Draft / Balanced / Final / Heavy Scene / Anti-flicker | Один клик по пресету меняет скорость рендера в разы |
| **M5** | **Resume и защита от падений:** сканирование папки вывода, докрутка недостающих кадров, ловля `out of memory` с конкретной подсказкой, авторетрай пачки с урезанными настройками, chunking | Убил процесс на середине — приложение дорендерило остаток само |
| **M6** | **ffmpeg-сборка секвенции в видео**, пресеты кодеков, уведомления, автовыключение | После рендера сразу лежит готовый mp4/mov |
| **M7** | Полная динамическая форма из capabilities (экспертный режим), состояние «не трогать», история в SQLite | Все свойства движка доступны, видно, что применилось |
| **M8** | PyInstaller-сборка `.exe`, иконка, онбординг | Один файл, который можно запустить с нуля |

Порядок изменён под реальные боли: падения по памяти и ручная рутина стоят дороже,
чем полнота настроек. Экспертная форма (бывший M4) уехала в M7 — до неё пресетов
из `02_RENDER_SETTINGS.md` хватает для 90% задач.

Костяк — M0–M3, после него приложение уже запускает рендер и показывает прогресс.

## 9. Принятые решения

- **Стек:** Python 3.11+ и PySide6. Вся логика в `core/` пишется **без импортов Qt**,
  чтобы слой интерфейса можно было заменить, не переписывая приложение.
- **Платформа:** Windows, одна машина. Сетевой рендер не закладываем.
- **Очередь:** модель задачи с первого этапа, UI — минимальный список. Без приоритетов
  и планировщика.
- **Сборка видео:** нужна, рабочий процесс идёт через секвенции. Этап M6.
- **Приоритет функций** (в порядке ценности): защита от падений и докрутка кадров →
  скорость через пресеты → автоматизация запуска и сборки → борьба с мерцанием →
  полнота настроек.
- **Исходный `.blend` не изменяется никогда.** Только override на время процесса.
