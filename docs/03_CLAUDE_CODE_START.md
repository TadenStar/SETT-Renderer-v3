# Старт проекта в Claude Code + GitHub
## Пошагово, Windows

---

## Шаг 1. Установить Claude Code

Открой **PowerShell** (не CMD) и выполни:

```powershell
irm https://claude.ai/install.ps1 | iex
```

Проверка:
```powershell
claude --version     # должно напечатать что-то вроде 2.1.211 (Claude Code)
claude doctor        # диагностика установки без запуска сессии
```

Если `claude` не распознаётся — закрой и открой PowerShell заново (обновляется PATH).

Что нужно знать:
- Node.js **не требуется**. Установка через npm считается устаревшей.
- Нативная установка обновляется автоматически в фоне.
- Нужна подписка **Pro, Max, Team, Enterprise** или аккаунт Console с кредитами.
  Бесплатный план Claude.ai доступа к Claude Code не даёт.
- **Git for Windows** формально не обязателен, но поставь: он даёт Claude Code
  доступ к Bash-инструменту, иначе используется PowerShell.
  Скачать: https://git-scm.com/downloads/win

Официальная документация: https://code.claude.com/docs/en/setup

## Шаг 2. Установить Git и GitHub CLI

```powershell
winget install Git.Git
winget install GitHub.cli
```

Настроить Git (один раз):
```powershell
git config --global user.name "Твоё Имя"
git config --global user.email "твой@email"
git config --global init.defaultBranch main
```

Авторизоваться в GitHub:
```powershell
gh auth login
```
Выбирай: GitHub.com → HTTPS → Yes (authenticate Git) → Login with a web browser.

```powershell
mkdir D:\Projects\blender-render-manager
```

## Шаг 5. Создать `CLAUDE.md`

Это файл контекста, который Claude Code читает автоматически в начале каждой сессии.
Самый важный файл в репозитории. Создай в корне:

```markdown
# BRM — Blender Render Manager

## Что это
Десктопное приложение под Windows для управления рендером в Blender через CLI.
Запускает `blender -b`, применяет настройки через генерируемый override-скрипт,
показывает живой прогресс, ведёт очередь задач.

Полное ТЗ: `docs/01_BRM_SPEC.md`
Настройки рендера и пресеты: `docs/02_RENDER_SETTINGS.md`
Читай их перед тем, как реализовывать что-либо в core/.

## Стек
- Python 3.11+
- PySide6 (Qt) — UI, QProcess для запуска Blender
- pydantic — валидация пресетов
- pytest — тесты
- Целевая платформа: Windows 10/11. Сборка через PyInstaller.

## Железо, под которое пишем
Legion 5 OLED, Intel i9, 32 GB RAM, RTX 5070 Laptop, одна машина.
Дефолты должны быть безопасны по VRAM и RAM. Никаких предположений о рендер-ферме.

## Архитектурные правила — не нарушать
1. Настройки применяются ТОЛЬКО через генерируемый override.py,
   передаваемый Blender'у через `--python`. Исходный .blend не изменяется никогда.
2. Каждое присваивание RNA-свойства идёт через `safe_set()` с проверкой `hasattr`
   и логированием. Имена свойств различаются между Blender 4.5/5.0/5.1/5.2 —
   хардкод запрещён.
3. UI настроек строится динамически из capabilities.json, полученного пробой
   реального бинарника Blender. Не описывать форму вручную.
4. Порядок аргументов CLI критичен: `-b file.blend ... -o ... -a`,
   аргументы Cycles только после `--`. См. спеку, раздел 5.
5. Процессы запускаются списком аргументов, не строкой. Чтение stdout —
   `encoding="utf-8", errors="replace"` (в путях бывает кириллица).
6. Парсер логов деградирует мягко: нет совпадения regex — показываем меньше данных,
   не падаем.
7. Никакой бизнес-логики в файлах ui/. Только отображение и сигналы.

## Команды
- Запуск: `python -m brm`
- Тесты: `pytest -q`
- Сборка: `pyinstaller --noconfirm brm.spec`

## Стиль работы
- Перед изменениями показывай план, жди подтверждения.
- Один этап (M0…M6 из спеки) = одна ветка = один PR.
- Каждая новая функция в core/ сопровождается тестом.
- Не добавляй зависимости без явного согласования.
- Комментарии и сообщения коммитов на русском, код и имена — на английском.
```

Правь этот файл по ходу проекта. Когда Claude Code делает одну и ту же ошибку
дважды — добавляй правило сюда, а не объясняй заново каждую сессию.

## Шаг 6. Первый коммит и репозиторий на GitHub

```powershell
git add .
git commit -m "Инициализация проекта: ТЗ, CLAUDE.md, gitignore"

gh repo create blender-render-manager --private --source=. --remote=origin --push
```

Одной командой создаётся приватный репозиторий, привязывается как `origin` и
заливается первый коммит. Проверить: `gh repo view --web`.

## Шаг 7. Запустить Claude Code

```powershell
cd D:\Projects\blender-render-manager
claude
```

Первый запуск попросит авторизоваться через браузер.

Дальше в сессии:

```
/init
```
Claude Code просканирует репозиторий и дополнит `CLAUDE.md`. Проверь, что он не
затёр твои правила — при необходимости верни их.

**Режим планирования:** нажми `Shift+Tab` дважды — Claude Code будет только
предлагать план, ничего не меняя. Для нового этапа всегда начинай с него.

## Шаг 8. Первая задача

Промпт для M0 (вставляй целиком):

```
Прочитай docs/01_BRM_SPEC.md и CLAUDE.md.

Реализуй этап M0:
- скелет приложения на PySide6, точка входа brm/__main__.py
- главное окно с заготовками панелей: Проект, Настройки рендера, Лог, Очередь
- модуль brm/core/storage.py: чтение и запись settings.json
  в %APPDATA%\BRM\settings.json, с pydantic-моделью
- диалог настроек с выбором пути к blender.exe
- валидация: файл существует и это исполняемый файл
- баннер-предупреждение вверху главного окна, если blender.exe не задан или
  путь протух, кнопка «Рендер» неактивна с поясняющим тултипом

Сначала покажи план файлов и их назначение. Код пиши после моего подтверждения.
Тесты для storage.py обязательны.
```

Дальше по этапам M1…M6 из спеки — тем же способом, по одному за раз.

## Шаг 9. Рабочий цикл

**Один этап — одна ветка:**
```powershell
git checkout -b m1-capabilities
```

Внутри сессии Claude Code:
- `/clear` — очистить контекст между несвязанными задачами. Делай это часто:
  замусоренный контекст напрямую ухудшает качество кода.
- `/compact` — сжать длинную сессию, сохранив суть.
- `Esc` — прервать, если Claude пошёл не туда. Не жди до конца.

**Коммит и заливка** (можно попросить Claude Code, можно руками):
```powershell
git add .
git commit -m "M1: проба возможностей Blender и кэш capabilities"
git push -u origin m1-capabilities
gh pr create --fill
```

После мержа:
```powershell
git checkout main
git pull
```

## Шаг 10. Проверка на реальном Blender

Модульные тесты не поймают главное. После M2 обязательно прогони руками на
настоящей сцене и сохрани сырой лог Blender в `tests/fixtures/` — на нём потом
строятся тесты парсера. Это самая ценная тестовая база в проекте: форматы вывода
разных версий Blender различаются, и только реальные логи покажут как.

## Что стоит держать в голове

**Claude Code видит только то, что в репозитории.** Спека в `docs/` — это не
документация для людей, это рабочий вход для агента. Чем точнее спека, тем меньше
итераций.

**Не проси реализовать всё сразу.** «Сделай приложение по спеке» даст тысячи строк,
которые невозможно проверить. Один этап за раз, с запуском после каждого.

**Каждый этап должен запускаться.** Не переходи к M3, если M2 не рендерит кадр.
Накопленный непроверенный код — главный источник тупиков в таких проектах.

**Правь CLAUDE.md постоянно.** Это дешевле, чем повторять инструкции.
